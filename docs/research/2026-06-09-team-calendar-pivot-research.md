# Team Calendar: Исследование Пивота

Дата: 2026-06-09

Цель: понять, зачем проект может быть нужен в эпоху ИИ-ботов, агентов и автоматизаций, и выбрать реалистичный пивот.

## Короткое Решение

Самая сильная версия проекта:

> Team Calendar помогает ИИ-ботам и автоматизациям назначать встречи с командой: показывает только свободные окна, принимает заявку, сохраняет ее и отправляет подписанное событие в n8n, Telegram, CRM или другую систему.

Главная ценность: человек или команда дают ИИ-помощнику возможность назначать встречи, сохраняя детали календарей закрытыми.

Рекомендуемое направление:

1. Целевая форма продукта: безопасный календарный слой для ИИ-ботов.
2. Первый проверяемый продуктовый шаг: прием заявок на встречи и запуск подписанных автоматизаций.
3. Минимальное доказательство: Telegram/n8n-бот получает свободные окна, человек выбирает слот, Team Calendar сохраняет заявку, n8n получает подписанное событие.

## Пользовательская Ценность

### Для Владельца Команды

Пользователь получает одну безопасную точку входа для записи на встречу с командой.

Практическая польза:

- меньше ручных переписок про время;
- одна ссылка или один инструмент для бота;
- заявка на встречу сохраняется в системе;
- после заявки автоматически запускается следующий шаг.

Пример: клиент пишет в Telegram-бот, просит демо, бот предлагает реальные свободные окна команды, клиент выбирает время, команда получает заявку и уведомление.

### Для Участников Команды

Участники подключают календарь и раскрывают только занятость.

Практическая польза:

- названия встреч остаются закрытыми;
- участники не отдают ИИ полный календарный контекст;
- команда может показывать общее свободное время без раскрытия личных деталей.

Пример: в календаре есть встречи с врачом, юристом, клиентами и кандидатами. Внешний человек видит только доступные окна.

### Для Создателя ИИ-Бота Или Автоматизации

Разработчик получает надежный календарный инструмент для своего сценария.

Практическая польза:

- бот запрашивает свободные окна через Team Calendar;
- Team Calendar проверяет время по календарям;
- заявка сохраняется с номером;
- повтор запроса не создает дубль;
- подписанное событие уходит в n8n, CRM, Telegram или другую систему.

Пример: n8n-сценарий ведет клиента до выбора времени, затем Team Calendar фиксирует заявку и отправляет событие в процесс обработки лида.

### Для Внешнего Человека

Внешний человек получает простой выбор времени.

Практическая польза:

- видит реальные свободные окна;
- выбирает слот без длинной переписки;
- получает понятный результат: заявка создана.

## Почему Сейчас Появляется Смысл

ИИ хорошо ведет разговор, но календарная запись требует строгой проверки. Ошибка в дате, часовом поясе или доступности ломает доверие быстро.

Для планирования встречи часто достаточно знать свободные окна. Детали календаря дают лишний риск: названия встреч, участники, личные события, внутренние проекты.

После выбора времени обычно начинается рабочий процесс: CRM, Telegram-уведомление, задача в трекере, письмо, форма, онбординг, счет, подготовка материалов. Поэтому заявка на встречу ценна как событие для автоматизации.

В текущем проекте уже есть важные части для этого сценария: Google FreeBusy, расчет слотов, публичная командная страница, заявка на встречу, подписанные вебхуки, самостоятельный запуск.

## Что Уже Есть В Коде

Активная рабочая копия: корень этого репозитория.

Сильные активы:

- обертка над Google FreeBusy: `src/infrastructure/google/freebusy.ts`;
- командная страница со слотами и фильтром участников: `app/(pages)/t/[shareId]/page.tsx`, `app/_components/team-page/*`;
- обработчик заявки на встречу: `app/api/booking/post-handler.ts`;
- подписанные командные вебхуки: `src/application/usecases/send-team-booking-webhooks.ts`, `src/domain/team-webhooks.ts`, `src/infrastructure/notifications/team-webhook-jwt.ts`;
- проверка целевого URL вебхука и защита от локальных и приватных IP-адресов;
- встроенный Postgres и путь для самостоятельного запуска;
- AGPL-лицензия.

Пробелы для рекомендуемого пивота:

- нет устойчивой таблицы заявок на встречу;
- нет идемпотентного ключа заявки;
- нет жизненного цикла заявки: создана, подтверждена, отменена, ошибка;
- нет токенов для ИИ-инструментов или внешних автоматизаций;
- нет минимальных ролей для безопасного управления вебхуками.

## Первичный Ресеч

Я проверил пять направлений:

1. Появляется ли отдельная категория календарных инструментов для ИИ-агентов.
2. Есть ли реальная ценность в приватности и строгой проверке календаря.
3. Насколько важны вебхуки и события после записи на встречу.
4. Насколько плотный рынок обычных календарных помощников.
5. Насколько текущий код подходит для пивота.

Основные источники:

- OpenAI Apps SDK строится вокруг MCP и позволяет приложениям работать внутри ChatGPT: <https://help.openai.com/en/articles/12515353-build-with-the-apps-sdk>
- режим разработчика ChatGPT поддерживает пользовательские MCP-приложения с действиями записи и изменения: <https://help.openai.com/en/articles/12584461-developer-mode-and-mcp-apps-in-chatgpt>
- MCP описывает строгий формат инструментов, результатов и ошибок: <https://modelcontextprotocol.io/specification/2025-06-18/schema>
- Google Calendar FreeBusy возвращает занятость календарей: <https://developers.google.com/workspace/calendar/api/v3/reference/freebusy/query>
- Google Calendar `freeBusyReader` позволяет открыть занятость без деталей событий: <https://developers.google.com/workspace/calendar/api/concepts/sharing>
- Cal.com описывает использование календарных действий ИИ-агентами: <https://cal.com/docs/agents>
- Calendly и Cal.com используют вебхуки как механизм событий после записи: <https://calendly.com/help/webhooks-overview>, <https://cal.com/docs/developing/guides/automation/webhooks>
- n8n и Zapier развивают сценарии, где инструменты и события запускают автоматизации: <https://docs.n8n.io/integrations/builtin/app-nodes/n8n-nodes-base.googlecalendar/>, <https://help.zapier.com/hc/en-us/articles/45394909914381-Set-up-your-agent-s-trigger>
- CalBench исследует приватность и координацию в календарных задачах для агентов: <https://arxiv.org/abs/2605.09823>
- Calendar.help показывает ценность структурированного процесса и человеческого подтверждения в агентском планировании: <https://arxiv.org/abs/1703.08428>

## Тезисы После Первичного Ресеча

### Тезис 1. Календарные Инструменты Для ИИ-Агентов Становятся Категорией

Что найдено:

- OpenAI Apps SDK и MCP дают понятный способ подключать инструменты к ИИ-средам.
- Cal.com уже документирует работу календаря для ИИ-агентов.
- Появились отдельные продукты вокруг календарного MCP, API для встреч и агентского планирования.

Что это значит для проекта:

Team Calendar может дать ИИ-боту маленький набор безопасных действий:

- найти свободные окна команды;
- создать заявку на встречу;
- проверить статус заявки;
- протестировать отправку события в автоматизацию.

### Тезис 2. Защищенность Календаря Дает Реальную Ценность

Что найдено:

- Google FreeBusy и режим `freeBusyReader` подтверждают: занятость можно раскрывать отдельно от деталей событий.
- Исследования календарных агентов выделяют конфликт между координацией и приватностью.
- Практические обсуждения вокруг ИИ-планирования упираются в надежность, повторные проверки, идемпотентность и подтверждение.

Что это значит для проекта:

Центральное обещание продукта:

> ИИ может согласовать время с вашей командой, не читая детали календарей.

Это обещание сильнее, чем ускорение записи на встречу. Ускорение есть у многих продуктов. Защищенный календарный слой для бота дает более узкую и понятную роль.

### Тезис 3. Событие После Заявки Часто Важнее Самой Страницы Записи

Что найдено:

- Calendly и Cal.com используют вебхуки для событий записи и отмены.
- n8n и Zapier делают ставку на сценарии, где событие запускает цепочку действий.
- В текущем репозитории уже есть подписанные события `booking.requested`, идентификаторы доставки, статусы доставки и защита URL.

Что это значит для проекта:

Team Calendar может стать надежным источником событий для автоматизаций:

- заявка создана;
- заявка подтверждена;
- заявка отменена;
- доставка события повторена;
- ошибка доставки записана.

### Тезис 4. Обычный Календарный Помощник Имеет Низкую Уникальность

Что найдено:

- Calendly развивает Callie, ИИ-помощника для согласования встреч по email.
- Reclaim продает ИИ-календарь и автоматическое планирование.
- Motion продает ИИ-планирование задач и календаря.
- Clockwise закрылся и направляет пользователей в сторону Reclaim, что показывает жесткость рынка.

Что это значит для проекта:

Широкая ставка на личный ИИ-календарь выглядит слабой. Сильнее выглядит узкая роль: командные свободные окна, приватность, заявка, подписанное событие для процесса.

### Тезис 5. Текущий Код Быстрее Ведет К Инфраструктурному Пивоту

Что найдено в проекте:

- FreeBusy уже есть.
- Расчет слотов уже есть.
- Заявка на встречу уже есть как маршрут API.
- Подписанные вебхуки уже есть.
- Самостоятельный запуск уже есть.

Что нужно добавить первым:

- таблицу заявок;
- идемпотентность;
- статус заявки;
- тест доставки вебхука;
- короткую инструкцию для n8n.

Это меньше по объему, чем полный план про роли, приглашения, историю членства и передачу владения.

## Варианты Пивота

### Вариант 1. Безопасный Календарный Слой Для ИИ-Ботов

Для кого:

- разработчики Telegram-ботов;
- создатели ИИ-ассистентов продаж и поддержки;
- люди, которые собирают процессы в n8n, Zapier, ChatGPT, Cursor, Claude;
- небольшие команды с чувствительными календарями.

Что получает пользователь:

- бот может запросить свободные окна команды;
- бот может создать заявку на встречу;
- Team Calendar проверяет слот;
- детали календарей остаются закрытыми;
- автоматизация получает подписанное событие.

Почему подходит проекту:

- уже есть FreeBusy;
- уже есть командная страница;
- уже есть заявка на встречу;
- уже есть подписанные вебхуки.

Риск:

- нужен аккуратный контракт API и документация;
- часть конкурентов уже идет в сторону календарного MCP.

Первый слайс:

1. `GET /api/agent/teams/:shareId/slots`
2. `POST /api/agent/booking-requests`
3. таблица `booking_requests`
4. идемпотентный ключ
5. событие `booking.requested` с постоянным идентификатором заявки

Оценка: самый сильный долгосрочный пивот.

### Вариант 2. Приемник Заявок И Запуск Автоматизаций

Для кого:

- n8n-сборщики;
- операционные команды;
- одиночные операторы, которые продают автоматизации;
- сообщества, где заявки надо отправлять в Telegram, CRM, Airtable, Linear или почту.

Что получает пользователь:

- ссылка или форма выбора времени;
- сохраненная заявка;
- подписанное событие;
- лог доставки;
- возможность повторить доставку.

Почему подходит проекту:

- текущий код уже ближе всего к этому варианту;
- вебхуки уже реализованы;
- первый полезный сценарий можно собрать быстрее.

Риск:

- без связи с ИИ этот вариант может выглядеть слишком маленьким.

Первый слайс:

1. таблица заявок;
2. лог доставки вебхуков;
3. кнопка тестовой доставки;
4. n8n-шаблон;
5. короткая инструкция подключения.

Оценка: лучший первый рабочий прототип.

### Вариант 3. Приватная Командная Страница Доступности

Для кого:

- маленькие команды;
- сообщества;
- консультанты;
- волонтерские группы;
- проектные команды.

Что получает пользователь:

- общую ссылку доступности команды;
- показ свободных окон;
- скрытие деталей событий;
- заявку на встречу с нужным участником или всей командой.

Почему подходит проекту:

- близко к текущему интерфейсу;
- понятно обычному пользователю;
- можно использовать и человеком, и ботом.

Риск:

- рынок страниц бронирования плотный;
- уникальность появляется только при связке с ИИ, приватностью и автоматизациями.

Первый слайс:

1. приватность команды по умолчанию;
2. минимальные приглашения;
3. сохранение заявок;
4. понятный статус подключения календарей.

Оценка: понятный, но менее сильный пивот.

### Вариант 4. Бэкенд Для Почтового Или Чат-Помощника

Для кого:

- ассистенты продаж и поддержки;
- рекрутеры;
- основатели и операторы с большим количеством переписок.

Что получает пользователь:

- помощник ведет переписку;
- Team Calendar дает безопасные окна;
- человек подтверждает слот по ссылке;
- заявка сохраняется;
- событие уходит в автоматизацию.

Почему подходит проекту:

- рынок уже идет к агентскому согласованию встреч;
- Team Calendar может быть строгой календарной частью такого помощника.

Риск:

- почта, доставляемость, контекст переписки и согласия делают этот вариант большим;
- Calendly уже движется в эту сторону.

Первый слайс:

1. оставить переписку внешнему боту;
2. дать боту только слоты и создание заявки;
3. подтверждение вести через Team Calendar.

Оценка: перспективно, но рано для первого шага.

### Вариант 5. Песочница Для Проверки Календарных ИИ-Агентов

Для кого:

- разработчики ИИ-агентов;
- исследователи;
- внутренние платформенные команды.

Что получает пользователь:

- тестовые календарные сценарии;
- проверку двойных броней;
- проверку утечек приватной информации;
- метрики успеха агента.

Почему подходит проекту:

- хорошо сочетается с соседними проектами про агентские системы;
- CalBench подтверждает исследовательскую ценность темы.

Риск:

- это больше инструмент для разработчиков;
- прямая пользовательская база уже.

Первый слайс:

1. тестовые календарные данные;
2. сценарии поиска слотов;
3. проверка конфликтов;
4. отчет по агенту.

Оценка: интересный исследовательский слой, вторичный по отношению к продукту.

## Ранжирование

1. Безопасный календарный слой для ИИ-ботов.
2. Приемник заявок и запуск автоматизаций.
3. Песочница для проверки календарных ИИ-агентов.
4. Приватная командная страница доступности.
5. Бэкенд для почтового или чат-помощника.

Целевое направление: вариант 1.

Первое доказательство ценности: вариант 2.

Логика выбора:

- вариант 1 дает проекту новый смысл в мире ИИ;
- вариант 2 быстрее всего превращается в рабочий сценарий;
- текущий код уже содержит большую часть варианта 2;
- после варианта 2 проще добавить API или MCP для ботов.

## Первый Проверяемый Слайс

Название: `booking-request-ledger-and-automation-proof`.

Цель:

Сделать сохранение заявок на встречи и доказать, что заявка может надежно запускать подписанную автоматизацию.

Объем:

- добавить таблицу `booking_requests`;
- хранить слот, автора заявки, выбранных участников, статус, ключ идемпотентности, исходное тело запроса;
- записывать заявку до отправки почты и вебхуков;
- возвращать `bookingRequestId`;
- добавить тест на повтор одного ключа идемпотентности;
- добавить страницу документации или раздел README для n8n-проверки подписи.

Границы первого слайса:

- полный жизненный цикл ролей и приглашений;
- почтовый ассистент;
- полноценный MCP-сервер;
- запись событий в Google Calendar;
- платежи.

Критерии успеха:

- заявка переживает сбой почты или вебхука;
- повтор того же запроса возвращает ту же бизнес-заявку;
- n8n получает подписанное событие с постоянным идентификатором заявки;
- детали календарей остаются закрытыми;
- сценарий можно показать на одном демо: бот, слоты, заявка, событие.

## Финальное Суждение

Проект сохраняет смысл в роли безопасного календарного слоя между людьми, ИИ-ботами, календарями и автоматизациями.

Самая понятная пользовательская формулировка:

> Дайте боту возможность назначать встречи с командой, сохраняя детали календарей закрытыми.

Самый прагматичный первый шаг:

> Превратить текущую заявку на встречу в сохраненную сущность и доказать путь до n8n через подписанное событие.

Если этот путь цепляет пользователей, дальше стоит делать API/MCP-инструменты для ботов. Если он не цепляет, проект лучше оставить как личный инструмент для самостоятельного запуска или закрыть.
