# Понимание задачи (PRD): Единый вход через Google и скрытое восстановление доступа

Дата: 2026-04-10

## Полезное действие
Пользователь нажимает одну кнопку `Продолжить с Google`, а продукт сам либо логинит его, либо создаёт аккаунт, либо незаметно переводит следующий вход в режим повторного подтверждения доступа, если связь с Google реально потеряна.

## Контекст (точка А)
- В интерфейсе сейчас используется формулировка `Войти через Google`, хотя фактически этот же flow и логинит returning user, и создаёт нового пользователя.
- В normal auth flow в `implementation/src/infrastructure/auth/auth-options.ts` жёстко указан `prompt: 'consent'`, поэтому returning user чаще, чем нужно, снова видит экран подтверждения Google.
- Продукт не различает на уровне контракта `hard auth loss` и временные ошибки Google.
- Ошибки календарной синхронизации схлопываются в общие сообщения вроде `Calendar sync failed`, из-за чего невозможно точно понять, когда надо перевести пользователя в повторный вход.
- Пользователь не должен видеть технические причины вроде `refresh token missing`, `reauth` или `Google credentials broken`.
- В продукте уже есть usable first-run path: пользователь без команд попадает в create-team flow.

## Цель (точка Б)
У пользователя есть один понятный CTA `Продолжить с Google`. Для обычного повторного входа Google consent не запрашивается лишний раз. Если сервер понимает по ответам Google, что доступ к календарю потерян именно у текущего пользователя, система помечает его Google-связку как требующую повторного подтверждения, завершает локальную сессию и на следующем нажатии той же кнопки автоматически запускает recovery-mode без новых терминов в интерфейсе.

## Метрики успеха
- Returning user в типовом повторном входе больше не проходит лишний consent screen по умолчанию.
- Новый пользователь проходит тот же CTA и попадает в usable first-run path без выбора между `входом` и `регистрацией`.
- При hard auth loss пользователь успешно возвращает доступ через тот же CTA без знания о токенах и без отдельной кнопки `Переподключить`.
- Количество продуктовых ошибок/обращений по теме “почему снова просит доступ к Google” снижается.

## FFF-рамка (Fixed time, Fixed budget, Flex scope)
- Fixed time: ближайший auth polish релиз после утверждения спеки.
- Fixed budget: один небольшой feature-slice без глубокого редизайна и без перестройки общего onboarding.
- Quality (не флексим): одна кнопка для пользователя, отсутствие техничных терминов в UX, отсутствие global forced-consent в normal flow, явное разделение hard auth loss и временных Google ошибок.
- Flex scope (можно резать): отдельный welcome-copy для первого входа, расширенный onboarding, отдельный экран помощи по recovery, дополнительная аналитика.

## MVP scope (минимально работоспособное полезное действие)
- [ ] Поменять guest CTA на `Продолжить с Google`
- [ ] Добавить supporting copy: `Войдём в существующий аккаунт или создадим новый автоматически`
- [ ] Убрать `prompt: 'consent'` из normal Google auth flow
- [ ] Ввести серверный признак `reauth_required` для Google account только при hard auth loss
- [ ] На hard auth loss инвалидировать локальную сессию и сохранять короткоживущий recovery-сигнал для следующего входа
- [ ] На следующем клике по той же кнопке запускать recovery-mode под капотом, не меняя visible CTA
- [ ] Различать `hard auth loss` и transient Google failure в use-case и infra слоях
- [ ] Оставить first-run через отсутствие команд без отдельной регистрации

## Non-scope (не делаем в MVP)
- Отдельные кнопки `Войти` и `Регистрация`
- Отдельный пользовательский CTA `Переподключить Google`
- Новый persisted onboarding/user-stage флаг
- Многошаговый onboarding
- Изменение Google scopes
- Редизайн popup completion

## Ограничения и риски
- Нельзя разлогинивать пользователя на любую Google ошибку: часть ошибок относится к сети или rate limit, а не к потере доступа.
- Нельзя определять `reauth_required` по aggregate availability flow команды, потому что ошибка может относиться к другому участнику или вообще к гостю.
- Если hard auth loss выявлен, но recovery-сигнал не переживёт logout, следующий анонимный клик не сможет автоматически перейти в recovery-mode.
- Forced-consent нельзя оставлять как глобальный fallback “на всякий случай”, иначе продуктовая цель не будет достигнута.

## Открытые вопросы
- Где именно в UI лучше всего показать neutral post-logout copy после hard auth loss: на landing, в toast перед logout или в query-driven status на guest surface.
