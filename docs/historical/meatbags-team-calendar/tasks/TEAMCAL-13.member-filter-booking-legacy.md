# TEAMCAL-13 — Фильтр слотов по участникам + URL deep-link + контекст бронирования

Статус: done

## Описание
Перевести фильтрацию доступности на странице команды в новый UX:
- список участников становится кликабельным фильтром;
- добавляется переключатель `Все` (командный режим);
- старый тоггл `Все свободны / Кто-то свободен` удаляется;
- при выборе участника показываются только его слоты;
- выбранный фильтр сохраняется в URL и восстанавливается при открытии ссылки;
- бронирование формируется с учетом выбранного фильтра;
- в попапе бронирования показывается read-only блок с подробной информацией, на кого бронируется слот;
- после отправки форма скрывается, попап не закрывается автоматически, внутри попапа показывается результат отправки.

## Принятые решения (зафиксировано)
1. Основной режим тоггла: `Все`.
2. Старый тоггл `Все свободны / Кто-то свободен` удаляем.
3. `Все` означает пересечение слотов всех участников команды.
4. Идентификатор в URL: `team_member_id`, query-ключ: `user`.
5. Обратная совместимость со старыми query-параметрами не нужна.
6. Бронирование учитывает выбранный фильтр:
   - если выбран один участник: слот и ссылка/участники календаря только для него;
   - если выбран `Все`: слот и ссылка/участники календаря для всей команды.
7. В карточке слота показываются только выбранный человек/люди.
8. Нужны только серверные логи (без клиентской аналитики).
9. В read-only блоке попапа выводим только имена (без email).
10. Заголовок попапа:
   - если выбран `Все`: `Бронирование {Название команды}`;
   - если выбран 1 участник: `Бронирование {Имя участника}`.
11. В popапе обязательно показываем подробную дату и время выбранного слота (read-only).
12. Если не хватает email для отправки (в т.ч. у целевого участника), отправка блокируется.
13. После отправки попап не закрывается, закрытие только вручную пользователем.
14. Вместо тоста показываем финальный текст результата прямо в попапе (persisted state).
15. Отдельный предупреждающий текст “уведомление уйдет только выбранным участникам” не нужен.
16. В режиме `Все` в read-only блоке попапа показываем имена участников списком.
17. Финальный текст после успешной отправки: `Встреча запрошена, команда скоро создаст встречу в календаре.`
18. При ошибке отправки (`500/502`) форма остается заполненной, попап не переключается в success-state, показывается тост с ошибкой.

## Scope (In)
- UI фильтра участников на `/t/:shareId`.
- URL-синхронизация фильтра через `?user=<team_member_id>`.
- Новый источник данных для карточек слотов с учетом выбранного фильтра.
- Передача фильтра в booking flow.
- Read-only блок в booking modal с деталями таргета бронирования.
- Success-state в booking modal после отправки (без формы и без автозакрытия).
- Серверное логирование availability/booking для нового фильтра.

## Scope (Out)
- Миграции БД и изменение схемы таблиц.
- Новые внешние интеграции (кроме текущего webhook).
- Обратная совместимость старых query-параметров.

## UX и поведение
1. Режим `Все` (по умолчанию):
   - URL без query `user`.
   - Слоты = пересечение доступности всех участников.
   - В карточках слотов показываются участники, относящиеся к текущему фильтру (`Все` => все участники слота).
2. Режим конкретного участника:
   - выбор кликом по участнику в списке;
   - URL: `?user=<team_member_id>`;
   - слоты только выбранного участника;
   - карточки слотов показывают только выбранного участника.
3. Невалидный `user` в URL:
   - fallback в режим `Все`;
   - URL очищается (удаляем query).
4. Booking modal до отправки:
   - заголовок динамический (`Бронирование {команда|участник}`);
   - read-only блок: кто является целями бронирования (только имена);
   - read-only блок: детальные дата и время выбранного слота;
   - форма ввода (email заявителя + комментарий).
5. Booking modal после успешной отправки:
   - форма скрывается;
   - остаются read-only данные о слоте и целях бронирования;
   - показывается итоговый текст статуса прямо в попапе;
   - попап остается открытым до ручного закрытия.
6. Booking modal при ошибке отправки:
   - форма остается видимой и заполненной;
   - success-state не показывается;
   - показывается тост с ошибкой;
   - пользователь может исправить данные и отправить повторно.

## Изменения API (предлагаемые)
### Availability
`GET /api/teams/:shareId/availability`
- новый query: `user=<team_member_id>` (optional)
- без `user`: текущая логика пересечения по команде
- с `user`: расчет только для выбранного участника
- при невалидном `user`: `400 { error: "Invalid user filter." }`

### Booking
`POST /api/booking`
- принять дополнительный контекст фильтра/участников слота (из текущего выбранного режима)
- сервер формирует целевой список участников для календарной ссылки по этому контексту
- если у цели бронирования нет email, сервер возвращает ошибку валидации
- payload в webhook должен явно содержать:
  - выбранный режим (`all` или `single`)
  - `selectedTeamMemberIds`
  - `selectedParticipantEmails`

## Пути пользователя
1. Пользователь открывает страницу команды и видит слоты по `Все`.
2. Пользователь кликает конкретного участника, получает его персональные слоты, делится URL с `?user=...`.
3. Получатель ссылки открывает URL и сразу видит тот же фильтр/слоты.
4. Пользователь бронирует слот:
   - в попапе видит read-only блок целей бронирования и слота;
   - отправляет заявку;
   - форма исчезает, попап остается открытым с результатом отправки;
   - в webhook и календарной ссылке фигурируют только участники текущего фильтра.

## Критерии готовности
- Старый тоггл `Все свободны / Кто-то свободен` отсутствует в UI.
- Фильтр участников работает кликом по участнику + режим `Все`.
- URL `user` синхронизирован с выбранным участником.
- Перезагрузка страницы сохраняет фильтр из URL.
- В режиме участника карточки и бронирование ограничены выбранным участником.
- В режиме `Все` карточки и бронирование включают всю команду.
- После успешной отправки booking:
  - тост не показывается;
  - попап не закрывается автоматически;
  - внутри попапа отображается статусный текст результата и read-only контекст.
- После неуспешной отправки booking:
  - форма остается заполненной;
  - показывается тост с ошибкой;
  - попап остается открыт.
- Серверные логи содержат фильтр и итоговый список участников для availability/booking.
- Unit-тесты обновлены по frontend и backend веткам фильтра.

## Тест кейсы
1. Дефолт:
   - открыть `/t/:shareId`;
   - ожидается режим `Все`, query пустой, слоты по пересечению всех.
2. Выбор участника:
   - клик по чипу участника;
   - ожидается `?user=<team_member_id>`, персональные слоты.
3. Прямой deep-link:
   - открыть `/t/:shareId?user=<team_member_id>`;
   - ожидается выбранный участник и корректные персональные слоты.
4. Невалидный user:
   - открыть `/t/:shareId?user=bad`;
   - ожидается fallback в `Все`, очистка query.
5. Карточки слотов:
   - в режиме участника карточка показывает только выбранного;
   - в режиме `Все` карточка показывает всех релевантных участников.
6. Booking в режиме участника:
   - открыть попап;
   - проверить заголовок `Бронирование {Имя участника}`;
   - проверить read-only блок целей бронирования (1 участник, только имя);
   - проверить read-only дату/время;
   - отправить, проверить серверный payload: только выбранный email/участник.
7. Booking в режиме `Все`:
   - открыть попап;
   - проверить заголовок `Бронирование {Название команды}`;
   - проверить read-only блок целей бронирования (имена всех участников);
   - проверить read-only дату/время;
   - отправить, проверить серверный payload: вся команда.
8. Success-state попапа:
   - после клика `Отправить` и успешного ответа форма скрывается;
   - попап остается открыт;
   - показывается итоговый текст внутри попапа: `Встреча запрошена, команда скоро создаст встречу в календаре.`;
   - закрытие происходит только вручную.
9. Ошибка отправки:
   - симулировать `500/502` от backend/webhook;
   - форма не очищается, остается заполненной;
   - показывается тост с ошибкой;
   - success-state не показывается.
10. Валидация email цели:
   - выбрать режим, где у целевого участника нет email;
   - попытка отправки должна быть заблокирована с явной ошибкой.
11. Серверные логи:
   - при availability лог содержит `shareId`, `mode`, `user filter`, `member count`;
   - при booking лог содержит `shareId`, `selectedTeamMemberIds`, `selectedParticipantEmails`, webhook status.
12. Мобилка:
   - на 360–430px чипы участников, тоггл `Все` и попап корректно отображаются без наложений.

## Риски и узкие места
- Расхождение между `team_member_id` и текущими id участников в ответах API.
- Гонки запросов при быстром переключении фильтров.
- Устаревшая URL-ссылка с удаленным участником.
- Ошибки синхронизации между видимым составом слота и payload бронирования.
