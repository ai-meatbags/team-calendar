# Выбор календарей для слотов и настройки команды — Техническая спецификация (v2)

Дата: 2026-02-04

## Контекст (текущее состояние)
- Backend: Express + Google OAuth + Google Calendar Free/Busy, хранение в NocoDB.
- Таблицы: `users`, `teams`, `team_members`, `sessions`.
- Сейчас free/busy берется только из `primary` календаря каждого участника.
- Поле владельца уже используется при создании команды.

## Цели
1. Каждый пользователь выбирает календарь(и) по умолчанию в настройках профиля.
2. Каждый пользователь может переопределить свой список календарей для конкретной команды.
3. Для подсчета слотов используются только выбранные календари (без фолбэков).
4. Минимальные OAuth-права: список календарей + free/busy, без доступа к событиям.
5. Редактирование команды: имя (только owner) и выбор календарей (все участники).

## Не делаем
- Чтение/запись событий.
- Редактирование календарей других участников.
- Миграции данных (пользователей еще нет).

---

## Google OAuth / Permissions
Минимальные scope:
- `https://www.googleapis.com/auth/calendar.calendarlist.readonly` — список календарей.
- `https://www.googleapis.com/auth/calendar.freebusy` — free/busy.
- `openid`, `email`, `profile` — идентификация.

Важно: никаких scopes с чтением событий (`calendar.readonly`, `calendar.events.readonly`).

## Модель данных (NocoDB)

### `users`
Добавить поля:
- `calendar_selection_default` (long text / JSON): дефолтный список календарей пользователя.

Формат `calendar_selection_default`:
```json
{
  "calendarId": { "id": "calendarId", "title": "Рабочий", "active": true },
  "calendarId2": { "id": "calendarId2", "title": "Личный", "active": false }
}
```

Правила:
- Список календарей **не хранится** отдельно. Хранится только `calendar_selection_default`.
- По умолчанию активен только `primary` календарь: `active: true` для primary, `active: false` для остальных.
- Время последнего обновления берется из системного `UpdatedAt` записи пользователя.

### `teams`
Добавить/зафиксировать:
- `owner_id` (string): ID владельца команды.

Что это такое:
- `owner_id` — идентификатор пользователя-владельца команды (берется из `users.Id`).
- Заполняется **только при создании команды** и **никогда не редактируется**.
- Используется для серверных валидаций любых ручек манипуляций с командой.

### `team_members`
Добавить:
- `calendar_selection` (long text / JSON, nullable): выбор календарей пользователя для конкретной команды.

Правило:
- Если `calendar_selection` отсутствует, используем `users.calendar_selection_default`.

## Задачи: Сервер

1) Инициализация календарей при первом логине
- Бизнесово: сразу есть дефолтный выбор календарей.
- Технически:
  - После успешного OAuth callback запрашиваем `calendarList.list`.
  - Формируем `calendar_selection_default` так, чтобы `primary` был `active: true`, остальные `active: false`.
  - Сохраняем в `users.calendar_selection_default`.

2) Загрузка списка календарей для настроек
- Бизнесово: пользователь видит актуальные календари и может выбрать нужные.
- Технически:
  - При открытии настроек профиля/команды запрашиваем у Google `calendarList.list`.
  - Определяем базовый выбор:
    - для настроек профиля — `users.calendar_selection_default`;
    - для настроек команды — `team_members.calendar_selection` текущего пользователя, если есть, иначе `users.calendar_selection_default`.
  - Мержим список Google с базовым выбором:
    - если календарь новый — добавить с `active: false`;
    - если календарь известен — оставить `active` как есть.
  - При простом открытии настроек в БД не пишем (обновляем только по кнопке “Сохранить”).

3) Сохранение дефолтного выбора календарей
- Бизнесово: пользователь фиксирует базовые календари для всех команд.
- Технически:
  - `PATCH /api/me/calendar` сохраняет `calendar_selection_default`.
  - Валидация: `calendarSelection` (только флаги `active`) должен быть подмножеством списка, полученного из Google.

4) Сохранение выбора календарей в команде (override)
- Бизнесово: участник может переопределить список календарей под конкретную команду.
- Технически:
  - `PATCH /api/teams/:shareId` сохраняет `team_members.calendar_selection` для текущего пользователя.
  - Если пользователь ничего не менял — просто не отправлять PATCH.
  - Валидация: `calendarSelection` (только флаги `active`) должен быть подмножеством списка, полученного из Google.

5) Управление командой (name/delete)
- Бизнесово: только владелец меняет название или удаляет команду.
- Технически:
  - `owner_id` проверяется на сервере для любых операций изменения команды.
  - `owner_id` не обновляется после создания.

6) Availability (free/busy)
- Бизнесово: слот свободен для пользователя только если свободны все его выбранные календари.
- Технически:
- Для каждого участника получаем эффективный выбор:
  - если есть `team_members.calendar_selection` — используем его;
  - иначе используем `users.calendar_selection_default`.
- Если список пуст/отсутствует — используем `primary` календарь (как раньше) и логируем предупреждение.
- `freebusy.query` по всем выбранным календарям.
- Busy пользователя = объединение busy-интервалов всех выбранных календарей.
- Дальше логика `all` / `any` для команды не меняется.

7) Логирование ошибок
- Бизнесово: прозрачность ошибок для пользователей и диагностика.
- Технически:
  - Сервер логирует ошибки free/busy и валидаций.
  - Клиент показывает ошибку и пишет в консоль.

## Задачи: UI

1) Профиль: дефолтный выбор календарей
- Бизнесово: пользователь задает базовый список календарей для всех команд.
- Технически (action points):
  - Добавить вход в “Календари” из пользовательского меню.
  - При открытии модалки → GET `/api/me/settings`.
  - Отрендерить список календарей с чекбоксами (по умолчанию активен только primary).
  - При клике “Сохранить” → PATCH `/api/me/calendar` с payload, где у каждого calendarId есть только `active`.
  - Показать успех/ошибку сохранения через готовую систему тостов Tailwind.

2) Создание команды: выбор календарей
- Бизнесово: сразу задать календарь(и) для расчетов в этой команде.
- Технически (action points):
  - Перед созданием команды показать список календарей (GET `/api/me/settings`).
  - Предвыбрать чекбоксы по `calendar_selection_default`.
  - При отправке формы POST `/api/teams` — передать только `active` флаги по всем calendarId.

- Бизнесово: каждый участник настраивает свои календари в этой команде.

  - При открытии → GET `/api/teams/:shareId/settings`.
  - Показать чекбоксы календарей (данные из ответа).
  - Поле имени команды доступно только owner.
  - При “Сохранить” → PATCH `/api/teams/:shareId` с payload только `active` по calendarId.
  - Показать успех/ошибку сохранения через готовую систему тостов Tailwind.

## API (новое/измененное)

### GET `/api/me/settings`
- Auth + same-origin.
- Действие: получает список календарей из Google и возвращает merged структуру.
- БД не обновляет.
- Ответ:
```json
{
  "calendarSelectionDefault": {
    "calendarId": { "id": "calendarId", "title": "Рабочий", "active": true }
  }
}
```

### PATCH `/api/me/calendar`
- Auth + same-origin.
- Payload:
```json
{ "calendarSelection": { "calendarId": { "active": true }, "calendarId2": { "active": false } } }
```
- Сервер использует текущий сохраненный список (с `id/title`) и патчит только `active`.
- Сохраняет `users.calendar_selection_default`.

### POST `/api/teams`
- Auth + same-origin.
- Payload:
```json
{ "name": "Название", "calendarSelection": { "calendarId": { "active": true }, "calendarId2": { "active": false } } }
```
- Сервер патчит `active` на основе `users.calendar_selection_default` и сохраняет в `team_members.calendar_selection`.
- Если не передан — ничего не делаем (используется дефолт).

### GET `/api/teams/:shareId/settings`
- Auth + same-origin + член команды.
- Действие: получает список календарей из Google и возвращает merged структуру для текущего пользователя.
- БД не обновляет.
- Ответ:
```json
{
  "team": { "name": "...", "shareId": "..." },
  "canEditName": true,
  "calendarSelection": { "calendarId": { "id": "calendarId", "title": "Рабочий", "active": true } },
  "calendarSelectionSource": "team"|"default"
}
```

### PATCH `/api/teams/:shareId`
- Auth + same-origin.
- Валидации:
  - пользователь должен быть членом команды;
  - если меняется `name`, то только owner (`owner_id`).
- Payload:
```json
{ "name": "Новое имя", "calendarSelection": { "calendarId": { "active": true }, "calendarId2": { "active": false } } }
```
- Сервер патчит `active` на основе текущего списка (team override или default) и сохраняет `team_members.calendar_selection`.

### GET `/api/teams/:shareId`
- Read-only данные команды и участники.
- **Не возвращает** список календарей и их выборы.

## Проблемы подхода (обсудить)
1. Нет кэширования списка календарей: при каждом открытии настроек делаем запрос к Google → больше latency и расход квоты.
2. Если Google API недоступен — пользователь не сможет открыть настройки и выбрать календари.
3. Если календарь удален/переименован, но пользователь не открывал настройки, в `calendar_selection_default` может остаться устаревший id/title → free/busy может падать до ручного обновления.
4. Новые календари не появятся в выборе, пока пользователь не откроет настройки.

---

## Валидации и правила
- `calendarSelection` (только `active` флаги) должен быть подмножеством списка, полученного из Google по `calendarId`.
- Фолбэк на `primary` допускается, если у участника нет активных календарей.
- Показываем все календари без фильтрации по `hidden`.

---

## Требуемые изменения в логике владельца
1. `owner_user_id_raw` заменить на `owner_id`.
2. Удалить логику автоназначения владельца в `GET /api/teams/:shareId`.
3. Заполнять `owner_id` только при создании команды.
4. Запретить любые обновления `owner_id` после создания.
5. Удаление и переименование команды — только owner.

---

## Бизнес-нюансы (добавить в требования)
1. Лимит числа календарей в free/busy — возможна ошибка `tooManyCalendarsRequested`.
   Нужен лимит выбора или разбиение запросов.
2. Календари с `accessRole = freeBusyReader` — поддерживаются, но событий нет (ожидаемо).
3. При потере доступа к календарю — возвращаем ошибку и предлагаем пересохранить выбор.
4. После добавления нового scope пользователи должны пройти пере‑согласование OAuth.
