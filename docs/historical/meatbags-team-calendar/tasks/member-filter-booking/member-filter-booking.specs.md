# Feature Specs — Member Filtered Availability + Targeted Booking

Статус: draft
Дата: 2026-02-12

## Контекст
Текущая страница команды показывает слоты в режимах `all/any` и не позволяет явно фильтровать доступность по конкретному участнику с deep-link через URL. Бронирование также не отражает выбранный контекст участников в UX и в серверном payload.

Новая фича должна:
- дать фильтр слотов по участнику;
- сохранить фильтр в URL;
- привязать бронирование к выбранному фильтру;
- сделать подтверждение результата отправки в самом попапе (без автозакрытия).

## Цели
- Быстрый просмотр доступности конкретного участника.
- Детерминированный deep-link: открытие URL восстанавливает фильтр.
- Прозрачный booking UX: видно, на кого бронируется слот и что произошло после отправки.
- Прозрачные серверные логи по фильтру и целевым участникам.

## Non-Goals
- Изменение прав доступа/ролей команды.
- Перестройка схемы NocoDB.
- Обратная совместимость со старыми query-параметрами фильтра.

## Технические ограничения реализации
Эта секция описывает только feature-level ограничения для этой фичи и не заменяет общие архитектурные правила.

1. Новый серверный код фичи реализуется в отдельном модуле, без масштабного рефакторинга legacy-кода.
2. `server/server.js` используется как composition root: wiring зависимостей и подключение роутов; новая бизнес-логика не добавляется в монолитные обработчики.
3. Серверная логика фичи строится через порты/адаптеры:
   - use-case слой не зависит напрямую от БД и внешних API;
   - инфраструктурные детали изолируются в адаптерах.
4. `member_public_id` для новых membership:
   - URL-safe формат;
   - immutable;
   - проверка коллизий при генерации.
5. Для обязательных пользовательских данных фичи запрещены неявные фолбэки и подмена идентификаторов.
6. Совместимость со старыми query-параметрами фильтра не поддерживается.
7. Старый переключатель `Все свободны / Кто-то свободен` удаляется в `TEAMCAL-16`.
8. Реализация остается минимально достаточной под текущие FR (без преждевременных расширений вне `TEAMCAL-15..19` и `TEAMCAL-30`).

## Зафиксированные продуктовые решения
1. Режим по умолчанию: `Все`.
2. Старый переключатель `Все свободны / Кто-то свободен` удаляется.
3. `Все` означает пересечение слотов всех участников.
4. Query-параметр фильтра: `member=<member_public_id>`.
5. Старые query-параметры не поддерживаем.
6. Бронирование зависит от фильтра:
   - выбран 1 участник: слот/ссылка/участники только для него;
   - выбрано `Все`: слот/ссылка/участники для всей команды.
7. В карточке слота показываются только участники текущего фильтра.
8. Аналитика на клиенте не нужна; нужны серверные логи.
9. В попапе read-only блок показывает только имена участников (без email).
10. Заголовок попапа:
    - `Бронирование {Название команды}` для `Все`;
    - `Бронирование {Имя участника}` для выбора одного.
11. В попапе показываем подробные дату/время выбранного слота.
12. Если у целевого участника отсутствует email, отправка блокируется.
13. После успешной отправки попап не закрывается автоматически.
14. При успехе форма скрывается, внутри попапа показывается текст:
    - `Встреча запрошена, команда скоро создаст встречу в календаре.`
15. При ошибке `500/502`:
    - форма остается заполненной;
    - success-state не показывается;
    - показывается тост с ошибкой.
16. Для залогиненного пользователя поле `email` в booking popup скрывается.
17. Для залогиненного пользователя requester email определяется только на backend из `req.session.userEmail`.
18. Если пользователь залогинен, но `req.session.userEmail` отсутствует, booking возвращает `400`.
19. `selectedParticipantEmails` и `attendeeEmails` в booking payload нормализуются и дедуплицируются (`trim + lower-case + uniq`).

## Функциональные требования
### FR-1. Фильтр участников
- Блок участников становится интерактивным фильтром.
- Добавляется явная опция `Все`.
- Активный фильтр визуально выделен.

### FR-2. URL sync
- `Все` -> query `member` отсутствует.
- Выбран участник -> `?member=<member_public_id>`.
- Невалидный `member` -> fallback в `Все` и очистка query.

### FR-3. Availability API
`GET /api/teams/:shareId/availability`
- Добавить optional query: `member=<member_public_id>`.
- Без `member`: расчет пересечения по всем.
- С `member`: расчет только выбранного участника.
- Невалидный `member`: `400 { error: "Invalid member filter." }`.

### FR-4. Состав участников в данных
`GET /api/teams/:shareId`
- Для каждого члена команды вернуть стабильный публичный идентификатор `member_public_id` (в JSON поле `memberPublicId`), пригодный для URL и фильтра.
- `member_public_id` хранится в `team_members`, генерируется при создании membership и не меняется.

### FR-8. Миграция существующих данных
- Для исторических `team_members` выполняется backfill `member_public_id` отдельным idempotent-скриптом.
- Миграция имеет режимы dry-run/apply и runbook запуска.

### FR-5. Booking targeting
`POST /api/booking`
- Принимать контекст фильтра и выбранных target-участников.
- Валидировать принадлежность выбранных `member_public_id` команде.
- Формировать целевые email только по выбранному фильтру.
- При отсутствии email у target-участника возвращать ошибку валидации.
- Для auth-запроса requester email брать из `req.session.userEmail`, игнорируя `body.email`.
- Для guest-запроса requester email брать из `body.email`.
- Для auth-запроса без `req.session.userEmail` возвращать `400`.
- Формировать `selectedParticipantEmails` и `attendeeEmails` с нормализацией и дедупликацией.

### FR-6. Booking popup UX
- До отправки: read-only блок (цели + слот), форма comment + условное поле email.
- Поле email:
  - показывается и обязательно для guest;
  - скрыто для auth.
- После успешной отправки: read-only блок + текст результата, без формы.
- При ошибке: форма остается заполненной, показывается error-toast.
- Попап закрывается только вручную.

### FR-7. Логирование
Логи availability:
- `shareId`, `duration`, `selectedMemberFilter`, `resolvedMemberCount`.
Логи booking:
- `shareId`, `selectedMemberPublicIds`, `selectedParticipantEmailsCount`, webhook status, итог клиентского ответа.
- Не логировать чувствительные данные сверх необходимого.

## Пользовательские сценарии
### US-1: Фильтр по одному участнику
1. Пользователь открывает `/t/:shareId`.
2. Выбирает участника.
3. Видит персональные слоты.
4. URL становится `/t/:shareId?member=<member_public_id>`.

### US-2: Возврат к общему режиму
1. Пользователь в режиме выбранного участника.
2. Нажимает `Все`.
3. Видит пересечение по всей команде.
4. URL возвращается к `/t/:shareId`.

### US-3: Deep-link
1. Пользователь открывает `/t/:shareId?member=<member_public_id>`.
2. Приложение автоматически выбирает нужного участника.
3. Слоты соответствуют фильтру.

### US-4: Бронирование в режиме участника
1. Пользователь выбирает одного участника.
2. Открывает слот.
3. Видит `Бронирование {Имя участника}` + read-only контекст.
4. Отправляет заявку.
5. Видит success-state в том же попапе.

### US-5: Бронирование в режиме Все
1. Пользователь в режиме `Все`.
2. Открывает слот.
3. Видит `Бронирование {Название команды}` + список имен участников.
4. Отправляет заявку.
5. Видит success-state в том же попапе.

### US-6: Ошибка отправки
1. Пользователь отправляет заявку.
2. Backend возвращает `500/502`.
3. Форма остается заполненной.
4. Видит тост ошибки, может отправить повторно.

## Критерии приемки (high-level)
- Фильтрация по участнику + `Все` работает и синхронизируется с URL.
- Старый тоггл `all/any` отсутствует в UI.
- Booking payload/ссылка учитывают выбранный фильтр.
- Booking popup реализует success/error состояния по правилам выше.
- Для auth-пользователя email не вводится в UI и берется из backend session.
- `attendeeEmails` не содержит дублей при пересечении requester/participants.
- Unit-тесты покрывают backend и frontend ветки новой логики.

## Декомпозиция и зависимость задач
Задачи находятся рядом с `specs.md` в этой папке:
- `TEAMCAL-15.backend-member-public-id-and-availability-filter.md` — Backend contract + availability filter.
  - включает `member_public_id` generation для новых membership.
- `TEAMCAL-16.frontend-member-filter-url-sync-and-slots.md` — Frontend filter UX + URL sync + slots rendering.
- `TEAMCAL-17.backend-booking-targeting-validation-logging.md` — Backend booking targeting + validation + logging.
- `TEAMCAL-18.booking-popup-readonly-success-error-state.md` — Booking popup UX state machine + FE integration.
- `TEAMCAL-19.member-public-id-backfill-migration.md` — Data migration backfill `member_public_id` (script + runbook).
- `TEAMCAL-30.booking-auth-email-source-and-dedup.md` — Auth/guest requester email source + popup email visibility + email dedup.

Параллельность:
- Сначала `TEAMCAL-15`.
- После `TEAMCAL-15` можно параллельно делать `TEAMCAL-16`, `TEAMCAL-17` и `TEAMCAL-19`.
- `TEAMCAL-18` стартует после готовности `TEAMCAL-16` и `TEAMCAL-17`.
- `TEAMCAL-30` стартует после `TEAMCAL-17` и `TEAMCAL-18` как доработка booking-контракта и popup UX.
- Прод-выкатка фичи блокируется до завершения `TEAMCAL-19`.

## Риски
- Несовпадение `member_public_id` между API team detail и availability/booking.
- Гонки запросов при быстром переключении фильтра.
- Расхождение отображаемых участников в слоте и таргета в booking payload.
