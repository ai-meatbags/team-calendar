# Понимание задачи (PRD): Персональные правила слотов и их пересечение в команде

Дата: 2026-04-11

## Полезное действие
Пользователь один раз настраивает свои личные правила показа слотов и бронирования, при необходимости задаёт отдельные правила для себя внутри конкретной команды, а продукт автоматически показывает итоговые правила команды как пересечение настроек всех её участников.

## Контекст (точка А)
- Сейчас правила `окно 14 дней`, `10:00—20:00 МСК` и `бронь минимум за 12 часов` захардкожены в availability runtime и частично дублируются в UI summary.
- Пользователь видит эти правила на public team page, но не может ими управлять ни в профиле, ни внутри команды.
- Идея “настроек команды” как отдельного редактируемого объекта оказалась слабой продуктово: слоты строятся как совместная доступность нескольких людей, значит и правила показа должны рождаться из их персональных ограничений, а не из произвольного team-wide значения.
- Owner-centric fallback тоже не подходит: он не отражает реальный состав участников, влияющих на availability, и делает модель искусственной.

## Цель (точка Б)
В продукте появляется персональная модель правил слотов:
- у пользователя есть личные настройки по умолчанию;
- в конкретной команде пользователь может задать отдельные настройки только для себя;
- editable “настроек команды” не существует;
- итоговые правила команды вычисляются как агрегат настроек участников команды;
- на public team page summary правил меняется вместе с member filter и всегда отражает тот же набор участников, по которому реально считаются слоты.

## Метрики успеха
- Пользователь может управлять своими личными правилами без участия разработки.
- Пользователь может задать отдельные правила для себя в одной команде, не меняя поведение в других командах.
- В настройках команды явно виден read-only итог пересечения по всем участникам.
- На public team page summary правил и сами слоты считаются по одному и тому же runtime member set.

## FFF-рамка (Fixed time, Fixed budget, Flex scope)
- Fixed time: один bounded feature-cut без изменения самой логики пересечения busy intervals.
- Fixed budget: ограничиваемся тремя rule-group, которые технически раскладываются на четыре поля:
  - окно показа слотов;
  - рабочее окно `с` / `до`;
  - минимальное время до бронирования.
- Quality (не флексим): один канонический contract для personal defaults, team personal overrides и агрегированных правил показа.
- Flex scope (можно резать): подсказки, пресеты, analytics, расширенные warning states для пустого пересечения часов.

## Non-scope (не делаем в MVP)
- Editable team-wide настройки слотов
- Настройка timezone
- Настройка длительности слота
- Частичный reset override по одному полю
- Роли “активный/неактивный участник”
- Специальная UX-обработка случая, когда агрегированное рабочее окно схлопывается

## Продуктовые ограничения и принципы
- Источник истины для правил слотов — персональные настройки участников, а не owner команды и не отдельная сущность “team settings”.
- Настройки команды как UI-секция существуют только в двух формах:
  - мои настройки для этой команды;
  - итоговое пересечение по команде.
- В настройках команды итог показывается по всем участникам команды, потому что это страница конфигурации состава команды, а не текущего booking-сценария.
- На public team page итог должен считаться по текущему runtime member set:
  - после member filter;
  - после тех же runtime checks, которые участвуют в availability;
  - без отдельного competing summary source.
- Для новых пользователей личные default-настройки создаются автоматически при регистрации со значениями текущего хардкода.
- Для существующих пользователей эти же значения проставляются миграцией.

## Контракт агрегации
Итоговые правила для набора участников считаются так:
- `days = max(individual.days)`
- `workdayStartHour = max(individual.workdayStartHour)`
- `workdayEndHour = min(individual.workdayEndHour)`
- `minNoticeHours = max(individual.minNoticeHours)`

Почему так:
- рабочее окно должно быть пересечением часов, иначе появятся слоты не для всех;
- минимальное время до бронирования должно уважать самого строгого участника;
- окно по дням вперёд берём как `max`, потому что продуктовая цель здесь — дать шанс найти доступного участника, а не резать горизонт самым консервативным правилом.

## Ограничения и риски
- Если оставить team-wide editable config, продукт снова получит искусственный источник истины, который не отражает реальные персональные ограничения.
- Если summary на public page не будет зависеть от member filter, UI начнёт врать о правилах текущей выборки.
- Если хранить всё в `users`, модель начнёт смешивать identity и отдельный bounded context настроек слотов.
- Если командный override хранить частично, усложнится reset semantics и возрастёт когнитивная нагрузка на UI.

## Открытые вопросы
- Нужен ли follow-up с предупреждением, когда агрегированное рабочее окно команды схлопывается в `start >= end`.
- Нужно ли в будущем показывать вклад каждого участника в итог пересечения.
